# Observability Design

## 1. Purpose

This document defines the practical observability design for the Infrastructure Automation Framework and its Out-Dialer reference platform.

It expands `adr/ADR-003-observablility-strategy.md` and the platform boundaries described in `docs/architecture.md`.

ADR-003 establishes observability as a first-class architectural concern built around three complementary signals:

- **logs**;
- **metrics**;
- **traces**.

This document describes how those principles are applied to the current reference platform and local demonstration environment.

The objective is not to implement a production telecom application. The Out-Dialer workload is intentionally synthetic. Its purpose is to provide a small distributed system with realistic component boundaries, asynchronous work, dependencies, failures, and state transitions so that modern observability practices can be implemented and exercised end to end.

The central design principle is:

> **Synthetic workload, real telemetry mechanisms.**

Application behaviour may be simulated, but metrics, logs, and traces should be generated by that behaviour and transported through mechanisms representative of real systems.

---

## 2. Architectural Context

The Infrastructure Automation Framework separates logical platform intent from deployment-specific implementation.

The Out-Dialer reference platform contains four logical compute nodes:

```text
Portal
Campaign Manager
Call Simulator
PostgreSQL
```

Their logical communication is:

```text
Customer
   |
   v
Portal
   |
   v
Campaign Manager --------> PostgreSQL
   |
   v
Call Simulator
   |
   +---------------------> results returned to Campaign Manager
```

These are logical platform components. A node does not inherently mean a Docker container, VM, Kubernetes Pod, or cloud instance. The current Docker Compose backend maps the logical nodes to containers for the local reference lab.

Observability must preserve this boundary. Telemetry describes logical application behaviour and runtime behaviour without making Docker-specific observability concepts part of the Platform Model unless a genuine platform-level requirement justifies them.

## 3. Observability Principles

### 3.1 Complementary signals

Following ADR-003:

- **metrics** describe numerical behaviour over time;
- **logs** provide detailed event and troubleshooting context;
- **traces** follow individual operations across component boundaries.

The signals should describe the same synthetic workload rather than independently generated data.

For example, a failed simulated call may:

1. increment a failure metric;
2. produce a structured log event;
3. mark the corresponding trace span as failed.

### 3.2 Business events over implementation details

Telemetry should describe meaningful domain events such as:

- campaign created;
- campaign queued;
- campaign execution started;
- simulated call completed or failed;
- campaign completed or failed;
- persistence operation failed.

Instrumentation should avoid insignificant implementation details merely because they are easy to measure.

### 3.3 Synthetic workload rather than synthetic telemetry

Avoid independently fabricating metric samples such as:

```text
campaign_queue_depth = random(0, 100)
```

when a small simulated queue can exist and the metric can report its actual size.

Counters should increase because simulated operations occurred. Durations should measure simulated operations. Logs and traces should describe those same operations.

This makes telemetry internally consistent and later correlation meaningful.

### 3.4 Vendor-neutral instrumentation

ADR-003 requires the application architecture not to depend directly on a specific observability backend.

Collection, storage, and visualization remain separate concerns. The target architecture is:

```text
                    Synthetic Out-Dialer
                           |
                  metrics / logs / traces
                           |
                collection / forwarding
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
      Prometheus          Loki             Tempo
          |                |                |
          +----------------+----------------+
                           |
                           v
                        Grafana
```

OpenTelemetry is the intended tracing standard. Grafana Alloy is the intended collector/forwarder as the observability stack evolves.

### 3.5 Incremental adoption

The initial implementation should produce a small number of useful signals, verify them end to end, and only then introduce additional telemetry or infrastructure.

The existence of a possible metric is not sufficient reason to add it.

## 4. Synthetic Out-Dialer Workload

### 4.1 Portal

The Portal represents the externally accessible API. Its simulated responsibilities are:

- accepting campaign creation requests;
- validating basic request input;
- submitting campaign work to the Campaign Manager;
- returning campaign identifiers;
- retrieving campaign status.

The Portal does not execute calls and does not directly access PostgreSQL. Its workload is primarily synchronous request/response traffic.

### 4.2 Campaign Manager

The Campaign Manager owns the asynchronous campaign lifecycle:

- accepting valid campaign requests from the Portal;
- creating campaign state;
- persisting campaign/work information;
- queueing and scheduling campaign execution;
- dispatching work to the Call Simulator;
- collecting execution results;
- updating campaign status and history.

The Campaign Manager is the only application component allowed to access PostgreSQL.

A successful Portal request means that campaign work has been accepted; it does not mean campaign execution has completed.

### 4.3 Call Simulator

The Call Simulator represents the execution worker:

- receiving campaign execution work;
- processing a synthetic list of destination numbers;
- introducing processing delays;
- generating synthetic outcomes such as success, failure, or timeout;
- returning execution results.

No SIP signalling, media processing, or real telephony integration is required.

### 4.4 PostgreSQL

PostgreSQL stores synthetic:

- campaign definitions;
- campaign status;
- work/execution state;
- execution results;
- history.

The data is fictional, but PostgreSQL may be a real runtime so that database interactions and database telemetry are genuine.

---

## 5. Campaign Lifecycle

The initial lifecycle remains deliberately small:

```text
created -> queued -> running -> completed
                       |
                       +-----> failed
```

A representative execution is:

```text
Customer
   |
   | create campaign
   v
Portal
   |
   | submit
   v
Campaign Manager
   |-- persist campaign
   |-- queue campaign
   |-- schedule execution
   v
Call Simulator
   |-- simulate calls
   +-- return results
   v
Campaign Manager
   |-- update state
   +-- persist history
   v
PostgreSQL
```

Telemetry must preserve the distinction between synchronous API handling and asynchronous campaign execution:

```text
Portal request latency != campaign execution duration
```

## 6. Initial Metrics

The first metrics should cover the service edge, asynchronous workflow, execution worker, and database dependency without creating an artificial production monitoring catalogue.

### 6.1 Portal

**`portal_requests_total`**

- Type: Counter
- Labels: `operation`, `status`
- Purpose: API throughput and failures

Initial operations may be `create_campaign` and `get_campaign_status`. `status` should use a bounded set such as `success` and `error`.

**`portal_request_duration_seconds`**

- Type: Histogram
- Labels: `operation`
- Purpose: Synchronous API latency

### 6.2 Campaign Manager

**`campaigns_total`**

- Type: Counter
- Labels: `status`
- Purpose: Campaign terminal outcomes

The initial terminal statuses should remain bounded, for example `completed` and `failed`.

**`campaigns_active`**

- Type: Gauge
- Labels: none
- Purpose: Campaigns currently executing

**`campaign_queue_depth`**

- Type: Gauge
- Labels: none
- Purpose: Campaigns waiting for execution

This is the primary backlog/saturation signal for the asynchronous workflow.

**`campaign_execution_duration_seconds`**

- Type: Histogram
- Labels: none
- Purpose: Asynchronous campaign execution duration

This should initially measure from execution start until a terminal execution state. Its semantics should remain stable once implementation begins.

### 6.3 Call Simulator

**`calls_total`**

- Type: Counter
- Labels: `result`
- Purpose: Simulated call throughput and outcomes

Initial result values may be `success`, `failed`, and `timeout`.

**`calls_in_progress`**

- Type: Gauge
- Labels: none
- Purpose: Calls currently executing

**`call_duration_seconds`**

- Type: Histogram
- Labels: none
- Purpose: Simulated call duration

### 6.4 PostgreSQL

Database telemetry should preferably originate from the real PostgreSQL runtime or an appropriate exporter rather than independently generated random values.

Useful areas include:

- active connections;
- transaction/query activity;
- errors;
- database response time where meaningful.

Application-side database operations may also appear in Campaign Manager telemetry when they represent meaningful application behaviour.

Exact PostgreSQL metric names are intentionally deferred until the exporter/instrumentation mechanism is selected.

### 6.5 Cardinality

Metric labels must use small bounded value sets.

Suitable:

```text
operation="create_campaign"
status="success"
result="timeout"
```

Do not use campaign IDs, request IDs, trace IDs, phone numbers, IP addresses, or arbitrary error messages as metric labels. Such identifiers belong primarily in logs and traces.

---

## 7. Metric Interpretation

Portal metrics describe service-edge health using RED concepts: rate, errors, and duration.

Campaign Manager metrics describe asynchronous workflow health: backlog, active work, execution latency, and failures.

A healthy Portal does not imply a healthy processing pipeline. For example:

```text
portal request latency             low
portal error rate                  low
campaign_queue_depth               rising
campaign execution duration p95    rising
```

This represents a responsive API with degraded asynchronous processing.

Call Simulator metrics describe worker throughput, concurrency, duration, and outcomes.

PostgreSQL and later node/container metrics describe dependency and resource health. This provides a useful separation between RED-style application analysis and later USE-style resource analysis.

---

## 8. Logs

Logs should describe the same lifecycle represented by metrics.

Representative events include:

```text
campaign accepted
campaign queued
campaign execution started
call simulation started
call simulation completed
call simulation failed
campaign completed
campaign failed
database operation failed
```

Logs should use structured logging and stable fields where practical. Useful contextual fields may eventually include:

```text
service
campaign_id
operation
status
trace_id
```

Unlike metric labels, identifiers such as `campaign_id` and `trace_id` are appropriate in logs because logs provide per-event diagnostic context.

ADR-003 logging principles remain applicable: use the logging framework rather than ad-hoc output and prefer meaningful domain events over implementation details.

---

## 9. Tracing

Distributed tracing is introduced after workload and metrics/logging paths are sufficiently stable.

A campaign flow should eventually be traceable conceptually as:

```text
campaign operation
|
+-- Portal span
|
+-- Campaign Manager span
    |
    +-- persistence span
    |
    +-- campaign execution
        |
        +-- Call Simulator span
```

Because campaign execution is asynchronous, tracing must not assume that the entire lifecycle is one synchronous HTTP request chain.

The implementation should preserve causal relationships across asynchronous dispatch where practical using OpenTelemetry context propagation or links appropriate to the eventual workload design.

Trace/span identifiers should be added to relevant logs to support navigation from traces to detailed events.

---

## 10. Signal Correlation

The long-term troubleshooting objective is:

```text
Grafana dashboard
      |
      | campaign execution latency increased
      v
Prometheus metric
      |
      | identify affected time window
      v
Tempo trace
      |
      | locate slow/failing component
      v
Loki logs
      |
      +-- inspect detailed campaign/call events
```

This requires metrics, logs, and traces to refer to the same underlying simulated operations.

---

## 11. Failure and Load Scenarios

The workload should eventually support deliberate operating modes.

### Normal

- small or empty campaign queue;
- low simulated failure rate;
- stable execution duration;
- responsive Portal.

### Busy

Campaign arrival rate exceeds execution capacity.

Expected effects:

```text
campaign_queue_depth increases
campaign_execution_duration increases
Portal may remain responsive
```

### Degraded Call Simulator

Additional failures, timeouts, or processing delay.

Expected effects:

```text
calls_total{result="failed"} increases
call_duration_seconds increases
campaign execution slows or fails
```

### Slow Database

Database interactions become slower.

Expected effects may include:

```text
Campaign Manager persistence latency increases
campaign throughput decreases
campaign queue may grow
```

The injection mechanism is an implementation decision. One injected condition should produce consistent effects across metrics, logs, and traces.

## 12. Infrastructure and Platform Telemetry

Application telemetry is one layer of the broader strategy in `docs/architecture.md`.

The wider design also includes:

- Ubuntu/runtime host telemetry;
- container telemetry;
- RouterOS telemetry;
- network-policy synthetic probes.

Conceptually:

```text
Application behaviour
        |
Container/runtime resources
        |
Host resources
        |
Network infrastructure
        |
Modeled communication policy
```

Synthetic network-policy probes are distinct from the synthetic application workload. They verify runtime behaviour against modeled communication intent, for example:

```text
DMZ -> Internal       expected ALLOW
Internal -> Database  expected ALLOW
DMZ -> Database       expected DENY
```

These signals can later support service and network SLIs/SLOs.

---

## 13. Observability Stack

The intended learning stack is:

```text
Metrics -----------------> Prometheus --+
                                        |
Logs -----> collector ----> Loki -------+--> Grafana
                                        |
Traces ---> OpenTelemetry -> Tempo -----+
```

Grafana Alloy is the intended collector/forwarder as the current Promtail-based logging path is modernized.

The objective is to understand the complete telemetry path and troubleshooting workflow rather than reproduce a production-scale observability platform.

---

## 14. Implementation Sequence

### Milestone 1 — Application metrics

1. implement the minimum synthetic Out-Dialer behaviour needed to generate coherent activity;
2. instrument the application components with the initial metrics;
3. expose metrics for Prometheus;
4. configure Prometheus scraping;
5. verify targets and raw metrics;
6. practice basic PromQL;
7. add a small Grafana application dashboard;
8. deliberately introduce one workload or scrape failure and troubleshoot it.

### Milestone 2 — Logging collection modernization

1. preserve existing logging behaviour;
2. replace the Promtail collection path with Grafana Alloy;
3. verify existing Loki queries/dashboard behaviour;
4. add structured synthetic application events where required.

This is a collection-layer refactoring and should not change the logical meaning of application logs.

### Milestone 3 — Distributed tracing

1. add Tempo;
2. introduce OpenTelemetry instrumentation;
3. trace representative Portal -> Campaign Manager -> Call Simulator activity;
4. preserve asynchronous causality;
5. verify traces in Grafana.

### Milestone 4 — Correlation

1. propagate trace context;
2. include trace identifiers in relevant logs;
3. configure Grafana signal links where useful;
4. demonstrate metric anomaly -> trace -> logs troubleshooting.

Infrastructure, RouterOS, and synthetic policy telemetry can then extend the same platform view.

---

## 15. Scope Boundaries

The observability workload exists to support infrastructure and SRE learning.

It is not a goal to build:

- a production campaign-management product;
- a real dialer;
- SIP or media processing;
- realistic telecom charging/billing;
- complex campaign business rules;
- large-scale queue infrastructure;
- a production HA observability stack;
- exhaustive application metrics;
- production-grade SLO/alerting infrastructure during initial milestones.

Application behaviour should be implemented only when it creates useful platform behaviour or telemetry.

The workload should remain small enough that an observed symptom can be reasoned about without first understanding a large application codebase.

---

## 16. Relationship to ADR-003

ADR-003 remains the architectural decision and source of the core observability principles. This document does not replace it.

ADR-003 established:

- observability as a first-class concern;
- logs, metrics, and traces as complementary signals;
- meaningful domain events over implementation details;
- structured logging;
- vendor-neutral architecture;
- incremental adoption.

The ADR initially focuses instrumentation on the `infra-automation` framework execution path itself, including the CLI, Loader, validators, and generators. That remains valid for observing the automation framework.

The Out-Dialer runtime is a second, complementary observability target:

```text
CONTROL / AUTOMATION PLANE
infra-automation
CLI -> Loader -> Validation -> Generators

RUNTIME / REFERENCE PLATFORM
Out-Dialer
Portal -> Campaign Manager -> Call Simulator
                    |
                    +----> PostgreSQL
```

The current observability phase primarily uses the Out-Dialer runtime for learning application metrics, distributed tracing, and cross-signal correlation because it provides long-running components, asynchronous execution, and meaningful service boundaries.

Framework telemetry and reference-platform telemetry should coexist rather than one replacing the other.

---

## 17. Design Summary

The Out-Dialer observability workload follows five rules:

1. **The workload is synthetic.** Campaigns, calls, timings, and failures simulate distributed application behaviour.
2. **Telemetry mechanisms are real.** Prometheus metrics, structured logs, and OpenTelemetry traces arise from workload execution rather than being independently fabricated.
3. **Signals describe the same events.** Metrics, logs, and traces should be correlatable wherever practical.
4. **Application and infrastructure signals are distinct but complementary.** Service behaviour, asynchronous workflow state, runtime resources, database health, and network-policy verification answer different operational questions.
5. **Implementation stays deliberately small.** Only behaviour required to create meaningful observability and troubleshooting scenarios should be implemented.

This provides a realistic observability learning environment while preserving the framework's core principle: logical platform intent remains independent of the technology used to realize and observe it.
